> 本文只描述 **Git Keymaster 应用内**的激活码实现：格式、验签、指纹、门控、吊销名单的消费方式。

## 第一部分 · 目标与非目标

### 1.1 功能目标

1. **一次性买断、真永久**：许可证不含版本上限，后续所有版本都能用。已售出的授权不因大版本失效。
2. **本机解锁**：用户粘贴激活码即可。验签、指纹比对、吊销检查都在本机完成。个人档口宕机不影响已购功能。
3. **抑制随手共享**，而不是防破解。验收标准不是「不可绕过」。
4. **换机可迁移，且绝不把用户锁死**：许可证失效只影响专业功能，不影响数据。

### 1.2 非目标

- **不做账号体系**。应用内没有注册、登录或在线激活。思源笔记的终身功能仍要登录账号校验购买记录，本设计不走那条路。
- **不做防逆向、加壳、反调试**。本仓库源码公开，纯客户端校验可以重新编译绕过。
- **不运营用户的云存储**。云同步依旧只把密文放到用户自己的 S3 / R2。
- **不把以下能力放进付费墙**：解锁（访问密码 / 恢复密钥 / 指纹）、数据导出、恢复密钥查看、立即锁定，以及全部本地 Git 身份能力。
- **不在应用里实现收款、webhook 或发信。** 购买按钮只打开浏览器。见个人档口的设计文档。

### 1.3 能力边界

离线校验只能证明「这串码由我签发」，不能证明「只有一个人在用」。

| 层 | 手段 | 挡得住 | 挡不住 |
|---|---|---|---|
| 1 | 硬件指纹绑定 | 把码转发给朋友、挂到论坛给别人用 | 自行改代码重编 |
| 2 | 吊销名单 | 退款或已泄露的订单在下次拉到名单后失效 | 停留在旧缓存、永不更新 |
| 3 | 许可证内嵌购买者署名并在界面显示 | 熟人之间顺手转发 | 匿名购买后公开 |

## 第三部分 · 与现有架构的契合点

### 3.1 许可证不复用更新包的 minisign

更新包验签已经在 `app/src-tauri/src/update/minisign.rs` 的 `verify_bytes`。那条路径继续只服务更新。

许可证用 **Ed25519 裸签名**（对规范文本签名，签名为 64 字节）。应用侧用 `ed25519-dalek` 验签，不把 `minisign-verify` 用于许可证。选裸签名是为了让个人档口能在 Cloudflare Workers 的 WebCrypto 里直接签，见个人档口的设计文档。应用只内置**公钥**。

两把密钥必须分开。更新包 minisign 私钥继续离线保管，泄漏后果是能给所有用户推送更新。授权私钥泄漏只能多签出专业版激活码，不能解密任何保险库。应用二进制里不出现授权私钥。

### 3.2 确定性文本

```68:74:app/src-tauri/src/update/manifest.rs
pub fn canonical_manifest_payload(manifest: &LatestManifest) -> String {
    let mut keys: Vec<&String> = manifest.platforms.keys().collect();
    keys.sort();
    let mut lines = vec![
        "git-keymaster-update-manifest-v1".to_string(),
        format!("version:{}", manifest.version.trim()),
    ];
```

许可证载荷沿用同一风格：带协议头的行文本，而不是签 JSON。`payload.rs` 与个人档口必须有字节级一致的测试。

### 3.3 门控落点

`app/src-tauri/src/sync/engine.rs` 的对外入口：`push_to_cloud`、`pull_from_cloud`、`pull_then_maybe_push`、`publish_after_edit`、`restore_from_cloud`、`list_snapshots`、`restore_snapshot`。在这些函数的第一行插入 `require_pro()?`。前端只读布尔 `isPro`，判断必须在 Rust 侧。

### 3.4 现有 `machine_id` 不能用作绑定依据


这是写在 `config.json` 里的随机 UUID，用途是仓库归属（`model/mod.rs` 的 `claim_unowned_repos` / `compose_cloud_repos`）。它会随配置文件被拷走。硬件指纹另做，两者不替代。

## 第四部分 · 许可证格式

这是应用与个人档口之间的契约。个人档口可以换支付渠道，不能改这些字节的含义。

### 4.1 载荷

```
git-keymaster-license-v1
order:gp_A7F3-2291
to:zhang@example.com
tier:pro
issued:2026-09-21
machine:b3:9f2c1a7e4d
machine:b3:71ad03c8bb
```

- `order`：订单号，吊销名单的唯一依据，全局唯一。渠道前缀由个人档口分配（如 `gp_`、`afd_`、`wx_`），应用只把它当作不透明字符串。
- `to`：购买者邮箱或昵称，设置页显示为「授权给 XXX」。
- `tier`：v1 只有 `pro`。
- **不设 `maxVersion`。** 真永久是商业前提。
- `machine`：指纹哈希，最多 3 行。零行表示不绑定（见第五部分）。

同一订单追加机器时，新码的载荷包含全部已绑定指纹。旧码仍然只对它里面写下的那些机器有效。吊销按订单号生效：该订单下所有历史激活码一起失效。载荷里不放签发代数。

### 4.2 激活码形态

`base64( 规范文本 + "\n---\n" + base64(64 字节签名) )`。界面按 5 字符分组。用户粘贴或手抄均可。

验签对象是分隔线之前的规范文本原文（含行尾，不含分隔线）。分隔线之后是签名的 base64。

### 4.3 存放位置

`config_dir()/license.txt`，与 `config.json` 并列。不进保险库、不进云同步。授权是本机事实。

## 第五部分 · 硬件指纹与申请码

新增 `sys.rs::hardware_fingerprint() -> Option<String>`：

| 平台 | 来源 |
|---|---|
| Windows | 注册表 `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid` |
| macOS | `IOPlatformUUID` |
| Linux | `/etc/machine-id`，回落 `/var/lib/dbus/machine-id` |

原值加固定盐后做哈希，只取前若干字节，形如 `b3:9f2c1a7e4d`。只存哈希。盐是编译期常量，写在 `license/` 里，个人档口不需要知道盐的原文：它只接收哈希。

禁止使用网卡 MAC、磁盘序列号、主机名。指纹读不到时只验签名即通过，并在设置页注明「本机无法读取硬件标识，授权未绑定本机」。宁可放过，不可锁死。

申请码是设置页展示的一段文本，供购买页和换机页填入，内容只有指纹哈希和应用版本，例如 `b3:9f2c1a7e4d@1.9.1`。一键复制。里面没有姓名、邮箱或密钥。

## 第六部分 · 吊销名单（应用如何消费）

不塞进 `latest.json`。`manifest.rs` 的 v1 确定性文本已定死，加字段会让已发布的旧版本验签失败。

应用只消费这份文本，用授权公钥验签：

```
git-keymaster-revocation-v1
issued:2026-09-22T00:00:00Z
revoked:gp_12345
revoked:afd_67890
```

检查更新时顺带拉取个人档口提供的 `revocation.txt`（地址见个人档口的设计文档）。验签后缓存。拉不到就沿用上次缓存，绝不因网络失败降级。名单只有订单号，不含邮箱。`issued` 必须新于本机缓存，拒绝回滚到旧名单。

谁在何时重签这份文件，由个人档口的设计文档规定。应用不持有签名私钥。

## 第七部分 · 应用内流程

### 7.1 激活

粘贴激活码后：解码、验签、比对本机指纹、对照吊销缓存、写入 `license.txt`、刷新 UI。失败原因要能区分：签名不对、指纹不匹配、已被吊销。

### 7.2 启动

读 `license.txt`，重复验签、指纹比对和吊销缓存检查，得出档位。任一步失败都静默降为免费版，原因写在设置页，不弹阻断对话框。启动过程不访问个人档口；吊销名单只在检查更新时刷新。

### 7.3 购买与换机入口

「设置 → 专业版」的购买按钮用系统浏览器打开 `https://pay.<域名>/?fp=<指纹>`。换机说明里的链接打开 `https://pay.<域名>/machines`。域名是编译期配置，缺省时按钮仍可复制申请码，由用户自行去购买页粘贴。

应用不内嵌支付页，不接收支付平台的回调。

## 第十部分 · 专业功能闭源 crate 拆分（M3 详解）

M1 与 M2 让「拿到合法码即可解锁」，但拦不住会读代码的人。本仓库公开，专业功能的实现字节全在源码里，`require_pro()` 只是一个返回 `bool` 的判断，改一行重新 `cargo build` 就绕过。这一部分是唯一能让「公开仓库编不出专业功能」成立的方案。是否投入由商业判断决定，技术上不是 M1 / M2 的前置条件。

### 10.1 先说清楚这一步能保护什么、不能保护什么

**能保护**：从公开源码「顺手重编一个免费绕过版」。专业功能的代码根本不在公开仓库里，`cargo build` 出来的二进制天生没有云同步引擎。这是相对 M2 的实质提升。

**不能保护**：

1. **协议本身可被第三方复刻。** 云同步是「标准 S3 / R2 + 用户自己的保险库密钥做端到端加密」。协议是公开的，数据在用户自己的桶里。有能力的人完全可以写一个自己的同步脚本。闭源保护的是「御钥师自带的一键同步体验」，不是「这份数据不可能被同步」。
2. **已发布的专业版二进制可被逆向。** 官方专业版通过 GitHub Release 公开分发，引擎代码就在里面。逆向去掉 `require_pro()` 检查是可能的，只是所需技能远高于改一行 Rust 重编。DRM 到此为止，别指望更多。

把目标定成「把绕过成本从『改一行』抬到『逆向二进制』」，而不是「不可破解」。

### 10.2 当前代码的耦合难题（拆分前必须正视）

`sync/` 不是一个可以整体挪走的叶子模块。它双向缠在核心里。

引擎向下依赖加密底座、数据模型与持久化：

调度器又反向依赖 `commands` 层的 `AppState` 和界面缓存：

```3:3:app/src-tauri/src/sync/scheduler.rs

```

直接把 `sync/` 移进新 crate 会立刻产生循环依赖：新 crate 要用 `commands`，`commands` 又要用新 crate。所以**先解耦、再拆分**，顺序不能反。

还有一个边界歧义必须先定：付费边界表把「导出」列为永久免费，但 `sync/backup.rs` 的 `export_vault_backup` / `import_vault_backup` 是本地 `.gambackup` 文件导入导出，属于「数据导出」，**不该进付费墙**。只有云端引擎（`engine` / `s3` / `scheduler` / 云端快照）才是专业功能。拆分时 `backup.rs` 里被引擎和克隆共用的函数（如 `deploy_key_to_workspace`）要下沉到公开底座，本地备份留在免费侧。

### 10.3 目标结构：一个 workspace，三个 crate

当前是单 crate `app`（`lib` 名 `app_lib`）。改成 workspace：

| crate | 可见性 | 产物 | 装什么 |
|---|---|---|---|
| `keymaster-core` | 公开 | rlib | `error`、`model`、`vault`、`store`、`sys`、`app_config`、`net`，以及本地 `.gambackup` 备份、`license`（验签 / 指纹 / 吊销）。免费功能与加密底座的全部。 |
| `keymaster-pro` | **闭源，独立私有仓库** | rlib | 云同步引擎：`engine`、`s3`、云端快照、`scheduler` 的纯逻辑部分。只依赖 `keymaster-core`，绝不依赖 `app`。 |
| `app` | 公开 | tauri 壳 | `commands`、Tauri 注册、UI 胶水、`main`。按 feature 决定是否链接 `keymaster-pro`。 |

依赖方向单向：`app → keymaster-pro → keymaster-core`，`app → keymaster-core`。`keymaster-core` 不认识另外两个，`keymaster-pro` 不认识 `app`。

`license` 放在**公开的** `keymaster-core`：验签是公开算法，公钥本来就要嵌进免费版（免费版也要能识别「这是一台已授权但当前免费的机器」并给出升级引导）。闭源的只有云同步引擎，不是许可证校验。

### 10.4 挂接机制：可选 git 依赖 + feature gate

`app/Cargo.toml`：

```toml
[dependencies]
keymaster-core = { path = "../keymaster-core" }
keymaster-pro = { git = "ssh://git@github.com/ice-juice/keymaster-pro.git", optional = true }

[features]
pro = ["dep:keymaster-pro"]
```

- **社区贡献者** clone 公开仓库，没有私有仓库权限，直接 `cargo build`（不带 `--features pro`）。Cargo 不会去拉那个 optional git 依赖，编出的是免费版，能跑、能测、能改除云同步外的一切。
- **官方发布** 在有私有仓库部署密钥的 CI 上 `cargo build --features pro`，链接进真实引擎。

引擎调用统一走一个 trait，免费侧编译一个 stub：

```rust
// keymaster-core：契约与免费实现
pub trait CloudSync {
    fn push(&self, vault: &Vault, cfg: &S3Config) -> Result<SyncResult>;
    // pull / snapshots / restore ...
}

pub struct Unavailable;
impl CloudSync for Unavailable {
    fn push(&self, _: &Vault, _: &S3Config) -> Result<SyncResult> {
        Err(AppError::ProUnavailable)   // 新增错误码
    }
}
```

```rust
// app：按 feature 选择实现
#[cfg(feature = "pro")]
pub fn cloud_sync() -> impl CloudSync { keymaster_pro::Engine::new() }
#[cfg(not(feature = "pro"))]
pub fn cloud_sync() -> impl CloudSync { keymaster_core::Unavailable }
```

`require_pro()` 与闭源是两道叠加的门，缺一不可：

| 场景 | `require_pro()`（许可证） | 引擎代码是否在二进制 | 结果 |
|---|---|---|---|
| 官方专业版 + 合法许可证 | 通过 | 在 | 解锁 |
| 官方专业版 + 无许可证 | 拒绝 | 在 | 挡在许可证门 |
| 社区自编免费版 + 伪造许可证 | 通过 | **不在** | stub 返回 `ProUnavailable` |

第三行正是这一步的意义：伪造许可证也没用，因为免费版根本没链接引擎。

### 10.5 Tauri command 与前端降级

云同步的 `#[tauri::command]` 始终注册（`cloud_sync_push` 等，见 `commands/sync.rs`），内部调用 `cloud_sync()`。免费版走 stub、返回 `ProUnavailable`；专业版走真引擎。

**不要**用 `#[cfg(feature = "pro")]` 让免费版干脆不注册这些 command——那样前端会收到「command not found」，还得区分「未付费」和「命令不存在」两种错误。始终注册 + 明确错误码，前端只认 `ProUnavailable` 一种，统一展示升级引导。前端的 `isPro` 仍只读一个布尔，判断在 Rust 侧。

### 10.6 先决重构（M3a，纯解耦，不涉及闭源）

这一步不动可见性，只把耦合理顺，公开仓库内即可完成，且能独立验证：

1. 把 `scheduler` 拆成两半：纯同步逻辑（输入 `Vault` + `S3Client`，无 `AppState`）下沉，可进 `keymaster-pro`；触发与界面缓存（依赖 `AppState`、`commands::sync`）留在 `app`。消除 `sync → commands` 的反向依赖。
2. 把 `backup.rs` 里被引擎和克隆共用的函数（`deploy_key_to_workspace` 等）下沉到 `keymaster-core`；本地 `.gambackup` 导入导出留在免费侧。
3. 在 `commands/sync.rs` 与引擎之间插入 10.4 的 `CloudSync` trait，command 只依赖 trait，不再直接 `use crate::sync::engine`。

做完 M3a，`sync/` 的纯逻辑部分变成一个只依赖核心、不被 `commands` 反向依赖的子树。这时再物理搬迁才安全。

### 10.7 拆分步骤（M3b）

1. 建 workspace，把 `error` / `model` / `vault` / `store` / `sys` / `app_config` / `net` / `license` / 本地备份迁入 `keymaster-core`，`app` 依赖它编译通过（此时还没有 pro，功能不变）。
2. 新建私有仓库 `keymaster-pro`，把 10.6 下沉好的引擎逻辑迁入，只依赖 `keymaster-core`。
3. `app` 加 optional 依赖与 `pro` feature，command 层按 10.4 切换实现。
4. 两套构建都要绿：不带 feature（模拟社区）保证公开仓库可编译可测；带 `--features pro` 保证官方版链接成功。

### 10.8 构建与发布流程

- **安装包形态不变。** 现有 `release.yml` 仍由 `tauri-apps/tauri-action` 打 NSIS / MSI、macOS universal、Linux 包，安卓走 `tauri android build`，iOS 走 `tauri ios build`。`prepare-lang.mjs`、`check-release-invariants.mjs`、安装包改名、更新包 minisign 签名都不动。品牌名、标题栏、文件名不受 crate 拆分影响。
- **变的是 action 传给 Cargo 的参数，以及拉取私有仓库的凭据。** 桌面、安卓、iOS 三条打包作业都要带上 `--features pro`（`tauri build` 里写在 `--` 之后，才会进 Cargo）。CI 用部署密钥让 Cargo 能 clone `keymaster-pro`，密钥只放在 secret，不进公开仓库。
- **官方打包必须在链接失败时停住。** 忘了 feature 或密钥时，Cargo 仍会编出能安装的免费版。发布作业要显式检查专业版符号已链进二进制，避免把 stub 装进 GitHub Release。
- **发布物默认带 `--features pro`。** 用户下载的仍是一个安装包，靠许可证解锁，不靠「换个安装包」。社区本地 `tauri build` 不带该 feature，打出来的是没有云同步引擎的免费包。

### 10.9 代价（这些是真金白银的成本）

1. **维护面翻倍。** workspace 三 crate、两套 CI、两个仓库同步版本号。`keymaster-core` 的公开 API 一旦被 `keymaster-pro` 依赖，就得当稳定接口维护，改动要跨仓库协调。
2. **贡献者无法完整验证涉及同步的改动。** 他们编不出专业版，改到 `CloudSync` trait 契约时只能看免费侧行为。涉及引擎的 PR 需要你在私有仓库这边补验证。
3. **一次性重构有风险。** `sync` 与 `vault` / `model` / `store` 缠得深（10.2），边界切错会在后续每次改动里反复付出跨 crate 成本。M3a 的解耦务必先独立做完、独立验证，再动物理搬迁。
4. **收益仍有天花板。** 见 10.1：挡得住源码重编，挡不住协议复刻和二进制逆向。

### 10.10 何时值得做

在稳定的付费转化出现之前不要做。M1 / M2 加个人档口已经能收钱，绕过的人此刻数量为零。M3 是「当盗版重编版开始在社区流传、且确实侵蚀收入」时的应对，属于按需触发，不是路线图上的默认下一步。真要做，M3a（解耦）无论是否最终闭源都有价值，可以先做，它让代码边界更干净；M3b（物理拆分与闭源）再按商业信号决定。
