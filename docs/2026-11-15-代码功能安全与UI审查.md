审查日期：2026-11-15。基线提交：`322f6c334a72a135a6cd72ebc16b7c68eff0b133`，**审查包含未提交工作树，不等同于这个提交或已发布安装包的审查**。审查期间其他开发任务持续修改文件；重点同步/Worker 文件在 03:12 UTC 记录了内容指纹，见文末。引用行号对应本轮读取版本。

本次只做审查与隔离验证，未修复业务代码、未操作真实保险库、真实凭据、云桶、设备或部署。本文是代码级风险评估，不是第三方安全认证，也不是所有平台的攻击验收。

## 1. 结论

**现有密码学原语选型合理，但当前实现尚不能满足“安全第一的密码、账号和隐私资料管理产品”的要求。** 主要短板是密钥生命周期与权限边界，以及备份、恢复、同步的完整性和故障处理；不是简单更换一个加密算法就能解决。

建议在本文 P1 问题修复并完成故障注入及恢复演练前，不将本产品作为用户重要密码、恢复码和证件的唯一保管位置，也不宣称已经具备跨平台一致的硬件绑定、彻底锁定、可靠完整恢复能力。这是针对已发现缺陷的产品准入判断。

按模块分配了三个子 agent：

| 审查分工 | 覆盖范围 |
| --- | --- |
| 核心加密与解锁 | Vault、KDF、密码/恢复信封、生物识别、会话、自动锁定、初始化及安全设置 |
| 同步备份与寄存柜 | S3、同步引擎、历史快照、离线备份、blob、Worker、分享及相应 UI |
| 隐私内容与 UI | 账号、TOTP、文件、笔记、重认证、剪贴板、草稿/缓存、桌面和移动交互 |
| 主 agent 交叉复核 | SSH/Git、更新链、Tauri 权限/CSP、测试、关键调用链复核与报告收敛 |

P1 表示应阻止按上述安全定位发布的高优先级问题；P2 表示需要排期的确定性功能缺陷、局部安全问题或故障一致性问题。**优先级不代表攻击无需前提**，每项均说明条件；没有将同用户恶意程序、内存读取、已解锁会话和普通远程访客混为一谈。

## 2. 加密机制是否合适

| 项目 | 当前实现及判断 |
| --- | --- |
| 主密钥 | OS CSPRNG 生成随机 256 位 MK，设计合理。`vault/crypto.rs:43` 起 |
| 对称加密 | XChaCha20-Poly1305，32 字节 key、24 字节随机 nonce、认证失败拒绝解密，选型合理。`vault/crypto.rs:15,100` |
| 密码派生 | Argon2id v0x13；内存下限 19 MiB、迭代下限 2；标定目标约 500 ms，默认跨设备上限 128 MiB。实际设备标定性能未实测。`vault/kdf.rs:11,73,106` |
| 恢复密钥 | 独立随机 256 位秘密，有版本前缀和录入校验；强度合理。校验码只用于纠错。`vault/recovery.rs:39` |
| 密钥隔离 | HKDF-SHA256 按密钥文件、元数据、同步对象、对象名等用途派生子密钥。`vault/crypto.rs:19,65` |
| 内存清理 | MK/恢复秘密本体有 ZeroizeOnDrop，但副本、KEK、缓存覆盖不完整，不能承诺所有明文用完即清零 |
| 生物识别 | Windows/Android 有系统密钥操作路径；iOS 明文 KEK 文件及 macOS 无生物识别 ACL 是实质差距，不能一概称硬件绑定 |
| 云端保密 | 密文上传和 HMAC 对象名是良好基础；但保密性不等于防回放、版本一致性、可恢复性 |
| 更新链 | 有 minisign 包签名、清单签名和版本地板，但二次获取清单的信任绑定不完整，见 R11 |

其他正面控制：生产 CSP 限制脚本来源、禁用 object/frame；S3 拒绝非 loopback 明文 HTTP 并禁用重定向；SSH 配置字段有换行和控制字符校验；默认开机免验证关闭、空闲锁 15 分钟、休眠锁开启、剪贴板清空 20 秒。

默认 5 分钟的查看免认证窗口是便利性取舍。建议隐私密码产品提供明确的“安全优先”默认档，并对恢复码轮换、导出全库等操作使用独立新鲜认证。

## 3. P1 问题：保密与防盗

### R01：iOS 生物识别 KEK 明文落盘

- 证据：`app/src-tauri/src/biometric/ios.rs:38-47,75-96`，随机 KEK 直接写入 `biometric-keys/<ref>.kek`；`biometric/mod.rs:224-240` 用其封装 MK，信封另存 `biometric.env`。
- 条件：攻击者取得可读的应用容器文件副本及加密工作空间。没有实测 iOS 系统备份是否包含该目录，也不是普通远程无认证漏洞。
- 影响：文件副本中同时存在解开 MK 的材料，不需要访问密码或真实 Face ID。应用在读取前弹生物识别不等于密钥被系统生物识别访问控制保护。
- 建议：使用 ThisDeviceOnly 的 Keychain 项和实际绑定 `biometryCurrentSet` 的访问控制；不具备 entitlement 时关闭该功能，不降级为明文 KEK。升级需迁移并删除旧 KEK，说明历史备份中旧副本的风险。
- 验收：导出测试容器只能取得密文和非敏感标识；改变录入集后旧密钥不可用；取消认证不产生可解密材料。

### R02：锁定仍保留完整 MK，后台还能重新填充明文缓存

- 证据：`commands/vault.rs:327-339` 明确保留 `sync_key`；`commands/mod.rs:136-138` 该字段是完整 MasterKey；`sync/scheduler.rs:47-56,167-180` 每次解锁都会捕获，未配置云同步也会保留；`:412-427` 用它打开独立 Vault，`:371-376` 读取机密；`store/mod.rs:267-270` 可重新填充明文缓存。
- 影响：README“立即锁定清内存 MK”不成立。该问题主要扩大锁定后内存读取/进程受损的暴露面，**未证明普通锁屏页面能直接显示密码**。
- 建议：严格锁定清所有 MK 副本，终止或隔离正在解密的任务，拒绝过期任务回填缓存。锁后同步只上传已准备好的密文；需要保留密钥的便利模式必须另行明确提示和主动选择。
- 验收：无同步配置、有同步配置、同步中锁定、休眠、后台恢复均检查密钥引用和缓存；锁定事件之后旧会话结果不得重新进入内存状态。

### R03：轮换恢复密钥不需要重认证

- 证据：`commands/vault.rs:505-513`、`vault/mod.rs:283-289` 只要求解锁状态；桌面 `pages/Settings.shared.tsx:1505-1512`、移动 `shared/hooks/useSettingsModel.ts:149-155` 直接调用。
- 条件：攻击者短暂操作用户已解锁的应用。
- 影响：不知道访问密码也可以建立长期全库恢复凭据，并让用户原恢复码无法解开最新头部。这比正常查看单个密码的权限更高，却少了二次认证。
- 建议：操作绑定的新鲜认证，不能复用普通查看宽限期；新恢复码安全保存确认与原子提交衔接，记录不含密钥的事件。
- 验收：仅有解锁态不可轮换；认证取消、超时、锁定或切库后票据失效；存盘失败不废弃原凭据。

### R04：笔记图片 IPC 可绕过文件保险库的二次认证

- 证据：`commands/files.rs:278` 列表返回附件 hash，`:464,519` 的正常导出/读取要求重认证；`commands/notes.rs:451-460` 的 `note_asset_get(hash)` 只检查已解锁，读取共享 blob 并返回完整 base64，不验证属于哪个笔记，也不限制只返回真实图片。
- 条件：已解锁会话中可发起该 IPC，或渲染器被控制；不等于锁定状态可读，也未证明有远程 XSS 入口。
- 影响：文件级“查看/导出需二次验证”边界不成立，掩码和受保护导出按钮无法补救后台另一条读取路径。
- 建议：按业务对象和用途统一授权；资产读取传 noteId/assetId 并核对引用归属与类型；共享 blob 的内容寻址不能充当授权。限制原始任意 hash 解密入口。
- 验收：对文件、账号图片、笔记资产做交叉读取矩阵；仅笔记权限不能读取文件附件；锁定、认证过期后均失败。

## 4. P1 问题：同步、备份和寄存柜防丢失

### R05：同步覆盖固定对象名，最后提交 manifest 仍会产生混代数据

- 证据：`sync/engine.rs:760-768` 按逻辑路径生成固定 HMAC 名并直接覆盖；`:826` 才写 manifest；`sync/s3.rs:248-255` PUT 无 If-Match/CAS；`engine.rs:899-918,233-243` 解密后未核对 manifest 中的 sha256/size。
- 场景：V1 已完成；V2 先覆盖 secrets，覆盖 accounts 或 manifest 前断网。云端仍展示 V1 manifest，但对象已部分变成 V2。另一端能通过 AEAD，却读到不同代的密码和元数据。双端同时写也有最后写入覆盖问题。
- 影响：同步成功/可解密不等于一致快照，后续合并可能选择错误机密。已有完整历史快照能救回部分数据，但不能保证刚产生的新变化已被备份。
- 建议：不可变版本对象或内容寻址对象；manifest 使用 ETag CAS；验证 hash、长度及上下文后整批提交本地状态；保留冲突版本而非静默覆盖。
- 验收：每个 PUT 阶段断网、两个设备同时改同一密码、旧对象重放、旧 manifest 重放，均不得静默混代。

### R06：历史索引读取失败仍执行 GC，可能破坏尚在保留的历史附件

- 证据：`engine.rs:782-791` 索引失败不传播，只不加入历史引用；`:1627-1634` 删除 live 集外 blob，发生在新 manifest 提交之前。
- 场景：当前记录删了附件 X，历史快照仍需 X；索引读取暂时超时，其余请求可用，X 被当垃圾删除。
- 影响：历史条目还在但附件不能恢复。历史内嵌笔记正文不能替代文件、账号图片、笔记附件的原始 blob（`:1159-1186,1386-1410`）。
- 建议：不能完整取得所有保留版本引用时禁止删除；提交和 GC 分离，延迟回收并提供回收窗口；对象存储版本化是额外防线。
- 验收：索引 403/超时/损坏时 DELETE 请求数为零；保留快照每个引用都能完整恢复。

### R07：备份/恢复静默缺项，却仍报告成功

- 证据：`sync/backup.rs:95-105` 私钥失败仅记日志；`:117-121` 多类数据读取失败变空列表；`:129-135` 缺 blob 仅日志；`:185` 返回成功。导入 `:308-327` 写元数据后吞掉 blob 写失败。历史恢复 `engine.rs:1474-1496` 先覆盖现用元数据，再忽略正文写入及附件拉取失败。
- 场景：冷缓存下 accounts 密文损坏、附件缺失、导入磁盘满、恢复时云存储临时不可用。
- 影响：用户误以为完整备份，换机或清理原库后才发现缺失；历史恢复也可能把可用现状换成不完整旧状态。基础 VaultData/Secrets 读取会传播错误，不是所有异常都被吞。
- UI 证据：`pages/Sync.shared.tsx:1237-1241,1318-1336` 成功/预览主要列身份、密钥、仓库计数，缺少完整隐私数据清单。
- 建议：完整备份默认遇缺项失败；抢救性部分导出必须显著标记“部分”、列缺失项。导入先暂存、验证所有引用和 hash，再提交；恢复前保存当前完整版本；成功含义是完成可恢复性验证。
- 验收：逐一损坏每种密文、移除每类附件、注入磁盘满和网络失败；不得绿色显示完整成功，不得覆盖唯一可用原库。

### R08：一次性取件在存储读取失败后仍耗尽次数，重试触发删除

- 证据：`services/file-locker-worker/src/handle.ts:309-325` 先减次数再 R2.get，异常无释放；`:410-412` 次数为零调用 burn；流式传输的失败分支也会焚毁（`:400`）。
- 已用当前 Worker、内存 SQLite 和 MemoryBucket 动态复现：注册 201 → 首次读取模拟 R2 异常返回 500 → 剩余次数 0 → 重试 404 → 对象不存在。
- 建议：领取租约/claim、幂等操作 ID、可续传下载；读取前失败必须释放保留次数。明确“发起领取”“服务端发出字节”“用户成功保存”的不同证据，不能声称服务器绝对知道用户已保存。
- 验收：R2 临时失败、断流、客户端重连、同一 claim 重试不丢文件；不同领取者受次数策略约束。

### R09：浏览器分享下载不能识别完整块截断

- 证据：`services/file-locker-worker/src/frame.ts:59-89` 仅逐块 AEAD/块序号认证，无认证总长度或终止记录；`download-client.ts:87-93` 只检查上限然后保存。
- 已动态复现：原文 `ABCDEFGH` 的两块密文解密为原文；移除最后整块后成功返回 `ABCD`；只留下 9 字节头则成功返回 0 字节。
- 条件：存储对象被有写权限方或故障替换成合法密文前缀，并按新长度正常提供。普通网络中断可能被 HTTP 长度检查发现，但不能覆盖此场景。
- 影响：用户把不完整的恢复资料当成功文件保存。Rust 寄存柜自取有 expected size，普通 vault blob 读取还有最终 SHA-256 校验，不能将本缺陷扩大成全部文件路径。
- 建议：认证总长度、总块数和结束标志，或用可信且经认证的完整摘要；整文件验证成功后才显示下载成功。

### R10：撤销分享会删除文件本体，客户端却还保留寄存条目

- 证据：`commands/locker.rs:843-860` 撤销后仅清 `entry.share`；Worker `handle.ts:255-265` 调 burn，`:437-445` 删除 R2 对象和记录。
- 影响：“停止对外分享”变成删除云端文件，随后用户自取也失败。若本地原文件还在可重传，但不应依赖原文件一直存在。
- 建议：私有寄存对象和分享授权分开建模；停止分享只撤销访问；删除文件需要独立动作和明确范围。
- 注意：已有寄存柜 V2 合约/方案讨论 claims、续传和停止分享，不应另外创建冲突方案。**方案或进行中的代码不等于旧 Worker 已修复**，需新旧客户端、服务端迁移一并验收。

## 5. P1 问题：更新供应链

### R11：已签清单与实际下载包在第二次获取时失去绑定

- 证据：`commands/update.rs:108-138` 先 fetch/验证清单，再 `updater.check()` 再取清单，只核对两次 version；`:147-164` 下载使用第二次结果。`update/checker.rs:27-52` 也存在同样分离。
- 已进一步阅读本机依赖 `tauri-plugin-updater 2.11.0/src/updater.rs:582-592,740`：下载 URL/签名来自第二次响应，验签对包字节进行，不验证第一份签名清单绑定的资产。
- 条件：攻击者控制更新源的响应，并持有一个高于客户端当前版本的真实已签清单和同钥签过的历史包。此项不意味着可以安装任意未签恶意程序。
- 影响：第一次交付真实签名新清单，第二次保留相同 version 但改成历史合法签名包，应用版本比较和包签名仍可通过；应用层防回滚失效，是否实际安装仍受具体平台安装器策略影响。官方未见过签名清单时允许无签清单的兼容路径也应收紧。
- 建议：使用单一已认证清单决定平台、URL 和 signature；若保留插件二次获取，必须将所有实际选择的安全字段与已验签资产逐项绑定校验，并校验同一包的摘要。正式安全版本关闭无签降级兼容。
- 验收：本地模拟更新源两次返回同版本、不同资产，必须在下载安装前拒绝。本轮未安装任何包或操作真实更新源。

## 6. P2 问题：功能一致性、数据保存与终端交互

### R12：本地多文件写入不具备事务性，且“原子写”会退回直接覆盖

- `commands/accounts.rs:296-297`、`commands/totp.rs:225-226` 删除先存 secrets、再存元数据；第二次失败，界面仍有条目但秘密已删除。新增/修改也有同类分步写入。
- `vault/mod.rs:274-289` 修改密码/恢复信封先改内存 header，落盘失败不回滚，造成内存与磁盘分叉；同文件 relax_kdf 已有可参考的回滚实现。
- `vault/mod.rs:430-464` rename 失败退回 `std::fs::write` 正本，存在截断后写失败的风险；成功即移除上一版本，且未见 fsync 耐久性保证。SSH 删除路径 `commands/write.rs:1054-1061` 也跨多个文件先删后写。
- 建议：统一事务/提交日志或版本目录+原子指针，持久化成功再更新内存；不能用直接覆盖作为安全存储降级策略；保留可恢复前版本。正常原子可见性与断电持久性分别测试。
- 验收：对每次写入注入失败、只读、文件占用、磁盘满、进程中断；重启后应是完整旧版或完整新版，不能半成功。

### R13：密码被 trim，保存值被改变；主密码解锁与重认证也不一致

- `commands/accounts.rs:104-111,230` 和 `shared/hooks/useAccountsModel.ts:386` 对账号密码 trim。合法第三方密码 ` abc ` 被存成 `abc`，会导致用户无法登录。
- 初始化/解锁允许原始带空格主密码，`commands/mod.rs:211` 重认证却 trim；同一密码可能能解锁、不能查看/编辑秘密。
- 建议：密码逐字节保存/验证，显示字段才做清洗。空字符串、全空白、缺字段应单独定义，不能静默改变已有秘密。回归覆盖新增、编辑、历史、复制、解锁、重认证、导入导出。

### R14：部分 Markdown 导出 PDF 会卡死界面

- `app/src/lib/notePdf.ts:30-98`：行首 `![` 但不符合 data/kmasset 图片规则时，既不进入图片分支，也不进入段落分支，循环不推进 i。
- 主 agent 在隔离 Node vm 中运行项目真实函数，普通 `hello` 成功；`![image](https://example.invalid/p.png)` 和 `![unfinished` 均触发 300ms 执行超时。未打开真实笔记。
- 建议：每轮保证推进；不支持/未闭合图片按普通文本回退；大文档解析有长度/时间限制，必要时放 Worker。UI 保留可取消和错误提示，不能无响应。

### R15：Android 剪贴板未实现与桌面相同的敏感内容保护

- `commands/secrets_ui.rs:35-44` Android 分支忽略 secret 与 clear_seconds；`ClipboardPlugin.kt:28` 普通 ClipData，无敏感标记；`:56-64` 清空时未判断是否仍是本应用写入的那份。
- 前端 `lib/secretsUi.ts:10-39` **确实有 JS 自动清空计时**，所以不能说完全没有清空。准确问题是依赖 WebView 生存与调度，后台/进程退出不能保证按应用配置时限清空；普通 ClipData 也可能被系统预览。到时无条件清空还可能清掉用户后来复制的其他内容。
- 建议：Android 原生设置敏感标记、维护本次复制标识和可用生命周期下的原生计时；仅清仍属于本次写入的内容。明确系统/后台限制，不将“不会进入任何历史”当绝对承诺。
- 验收：前台、后台、退出、系统预览、期间复制其他内容等真机场景。本轮没有真机验证。

### R16：笔记明文图片缓存跨锁定保留，旧异步结果仍可写回

- `pages/Notes.shared.tsx:26,128-174` 模块级 Map 保存完整 data URL，没有锁定/换库清理；取消组件只阻止 setState，仍先 `assetCache.set`，预加载也无会话校验。
- 影响：页面卸载不等于清除明文图片；锁定后仍有驻留数据及旧请求回填。并未证明普通锁屏 UI 会显示该缓存，也不能承诺 JS 字符串清引用后物理内存立即擦除。
- 建议：统一敏感缓存管理，用 workspaceId+sessionEpoch 隔离，锁定清引用、撤销对象 URL，拒绝旧响应；限定容量。回归覆盖读图未完成时锁定和切换工作空间。

### R17：SSH 投放路径按显示名生成，重复名称会覆盖已有密钥文件

- `commands/write.rs:203,239-255,400-408,565-566` 用清洗后的名称生成固定路径并直接 write，没有按 keyId 隔离或冲突检查；`sys.rs:647-687` 不同名称也可能清洗成同一 stem。
- 场景：工具连续保存两把同算法、空/相同名称但不同指纹的密钥，或身份名清洗后冲突。库内 ID 不同，但部署文件指向同一路径；既有 SSH 身份可能改用第二把密钥，删除其中一个也可能删掉共享部署路径。
- 影响：SSH 认证失败或身份混淆；加密库中原始 key 仍可能存在，不能说一定不可恢复。
- 建议：文件名包含不可变 keyId；显示名仅作标签。写入使用排他创建/显式替换流程；删除前检查实际引用所有权。用两个同名不同指纹身份验证文件、配置和删除隔离。

## 7. 需要补齐的安全设计，而非一律当成漏洞

1. **泄露后恢复**：修改访问密码/恢复码只是重新包裹同一 MK。持有旧头部和旧凭据的人仍能恢复旧 MK，不能因此撤销其对未来同 MK 数据的解密能力。需要独立“密钥疑似泄露”流程：新 MK、全量重加密、设备及云凭据撤销、历史副本风险说明。普通改密保持 MK 不是单独的实现错误，错误在于把它宣传成完全撤销。
2. **macOS 声明**：`biometric/macos.rs:1-8,117-129` 是普通钥匙串+独立 LAContext，未绑定生物识别 ACL；仍有系统钥匙串保护，不能说与 iOS 明文同等，也不能直接称任意进程无提示可读。应如实标明安全级别并补系统访问控制。
3. **主密码与 KDF**：后端仅拒空串，UI 最小长度不能代替统一口令策略；离线猜解不受登录延迟保护。`vault/header.rs` 对 iters 无上限，外来/损坏头部需做资源预算校验，避免极长计算；不可直接修改合法历史 KDF 参数后再解密。
4. **清零范围**：`session.rs` 的普通 Vec、DPAPI 输出复制，`vault/envelope.rs` 的 KEK/MK 中间副本及 macOS缓存需 Zeroizing 或显式零化；释放内存不等于擦除。对交换页、转储、管理员或内核控制的能力边界保持现实。
5. **SSH 使用能力**：锁定/退出不卸载已加载到 ssh-agent 的密钥，加载也未设置寿命，见 `agent/mod.rs:287-358` 和 `commands/vault.rs:327`。应明确“保险库锁定”是否同时撤销签名能力；默认可采用有期限且仅卸载本应用管理的 key，不应清掉其他程序的 agent 密钥。
6. **SSH 临时明文**：macOS 默认临时文件加载，其他平台有失败回退；普通删除无法保证 SSD 安全擦除，进程崩溃可能残留。Windows 是先写再收 ACL，收权失败仍继续（`agent/mod.rs:331-344`）。严格模式需减少临时明文，权限建立失败应中止，崩溃恢复只清理自己可证明拥有的文件。
7. **遗忘密码**：恢复码解锁后还缺顺畅的新访问密码绑定流程，原 change_password 仍要旧密码；新库恢复可间接解决，不应描述为必然失去数据。需要明确恢复后的重认证与设备重新绑定体验。
8. **防误删**：factory reset 已有两阶段确认和输入“清空”，不是无确认删除；建议增加可验证备份提醒、删除范围清单和短期隔离回收。也不能声称应用能阻止同用户/管理员直接删磁盘文件。blobs/icons 的残留范围应与“彻底清空”文案统一。
9. **备份覆盖**：离线备份/历史快照未包含完整 LockerData。临时传输功能可以排除，但 UI 必须明示；若改为永久寄存，就必须把取回密钥、记录、附件与恢复纳入同一保证。
10. **浏览器分享的信任**：CK 在 URL fragment 不随普通 HTTP 请求发送，是被动存储保密措施；提供下载 JS 的主动恶意/受损服务端仍能读 fragment。需说明此信任边界，不宣称可以抵御任意恶意服务器代码。
11. **密码和 TOTP 同库**：可用性好，但库失守会同时暴露两个因子。可为高价值账号提供独立验证器建议、仅存密码模式及独立紧急恢复资料，而不是让用户误以为同库等于独立安全域。

## 8. UI 与产品交互建议

UI 审查采用桌面/移动源码和仓库现有安全设置、隐私账号截图。截图是历史设计证据，**没有把它当作当前工作树的实时渲染**；未完成本轮真机、键盘无障碍、窄屏/深色模式验收。

当前按平台聚合账号、掩码、搜索分组、展开/折叠、独立查看/复制动作值得保留。对这个产品，优先修正状态语义和危险操作，不宜先做装饰性重设计。

| 界面 | 建议的可见行为 | 原因 |
| --- | --- | --- |
| 全局安全状态 | 分别显示“库已锁定”“后台是否保留解密能力”“SSH agent 是否仍可使用”；严格锁定成为明确动作 | 让用户理解实际边界，R02 |
| 设置/恢复码 | 轮换先新鲜认证；展示新码后验证保存；清晰列出哪些设备/副本受影响 | 防临时会话接管和自锁，R03 |
| 账号/文件 | 每条读取路径采用一致认证语义；查看倒计时到期遮盖，锁定撤销旧结果 | 掩码不能代替授权，R04/R16 |
| 备份与恢复 | 列账号、历史密码、TOTP、文件数/字节、笔记/图片、SSH、寄存柜覆盖；显示完整/部分/失败和缺失清单 | R07；“导出成功”不等于“可恢复” |
| 同步 | 区分本地已保存、远端已提交、存在冲突、恢复点已验证；冲突保留双版本 | R05，不把所有状态合成绿色勾 |
| 寄存柜 | 停止分享、删除文件、到期清除分开；显示领取中/可续传/次数状态 | R08/R10；不把已发出视为已保存 |

## 9. 建议整改顺序与验收门槛

### 第一批：建立不可绕过的秘密边界

R01/R02/R03/R04/R11；同时统一秘密副本与缓存生命周期、敏感操作认证票据和平台能力描述。先定义威胁模型与状态机，再实施。不得以升级文案代替修复。

### 第二批：建立可证明的防丢失能力

R05/R06/R07/R12；不可变远端对象、CAS、完整性清单、本地事务、失败不改现用库、延迟 GC。至少实现：干净新设备恢复、损坏备份拒绝、离线冲突双版本保留、写盘失败重启回滚、随机阶段断网恢复。

### 第三批：完成寄存柜协议与状态语义

R08/R09/R10 按现有 V2 方案收敛；服务端、网页、原生端及内嵌 Worker 版本一致验证，明确旧分享的兼容/撤销策略。不把临时寄存当唯一备份。

### 第四批：修复日常功能和 UI 安全反馈

R13—R17，以及平台差异、恢复引导、可访问性。安全反馈应与真实后端提交结果绑定。

正式安全验收至少包括：

- 静态/单元：所有 IPC 的锁定、认证过期、跨对象授权矩阵；密码原样往返；解析器终止性。
- 故障注入：单文件写失败、多文件中断、磁盘满、权限拒绝、云端 403/500/超时、混代/回放、并发设备冲突。
- 恢复演练：用导出的备份在独立空工作空间恢复全部种类，逐项校验数量与明文摘要；不以“能解密一个 JSON”代替恢复验收。
- 平台实机：Windows Hello、Android Keystore、iOS Keychain、macOS ACL；录入变化、认证取消、休眠/锁屏、进程退出及剪贴板。
- 发布：固定候选快照后全量构建/测试；依赖与供应链审计、签名链和旧包回放试验；再做独立安全复核。
